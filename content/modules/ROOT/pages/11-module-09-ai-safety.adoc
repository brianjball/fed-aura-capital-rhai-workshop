Fed Aura Capital operates in a heavily regulated industry. ECOA prohibits discriminatory lending. ATR/QM requires verified ability-to-repay calculations. TRID mandates accurate disclosures. == The Secure Agent Onboarding Story

This module represents the culmination of Wave 4: Secure Agent Onboarding. The core insight is that Red Hat is not building another agent framework. Customers pick their own harness - whether that's LangGraph, Claude Code, OpenClaw, ADK, Strands, or something custom. The gap they keep hitting is: how do I take this agent to production safely? Red Hat provides the secure onboarding layer: identity, policy, tracing, and composability, regardless of how the agent was built.

OpenShell is the kernel of that story. It packages the security primitives (syscall filtering, binary-level network policy, transparent credential proxying, and OCSF audit logs) into a single abstraction layer. It delivers this through three components:

* *CLI/SDK* - The developer interface. Runs on a laptop or CI system and connects to one or more gateways. Developers use it to create sandboxes, apply policies, and manage providers
* *Gateway* - The control plane, running as a pod in the cluster. Manages sandbox lifecycle, policy distribution, provider credentials, and communicates with the Agent Sandbox Controller for pod scheduling (including warmpool support for lower cold-start times)
* *Supervisor* - PID 1 inside every sandbox pod. Sets up isolation (seccomp, Landlock, network namespaces), starts the agent process, intercepts all outbound network traffic via an in-process proxy, enforces OPA policies, routes inference requests with credential injection, and streams structured security audit events (OCSF v1.7.0)

The model is deny-by-default: agents can access nothing unless explicitly permitted through YAML-based security policies. This is the difference between "deploy and pray" and a validated security posture with documented evidence.

=== Two BYOA Integration Patterns

*Pattern 1: Whole-agent sandboxing.* You package your agent (harness, config, dependencies) into a container image. OpenShell wraps it in a sandbox with policy enforcement, credential injection, and audit logging. No code changes to the agent are needed. This works for Claude Code, Codex, OpenCode, Gemini CLI, and others out of the box.

*Pattern 2: Harness-native integration.* Some frameworks (OpenClaw, Hermes) have built OpenShell plugins into their agentic loop. The harness decides when to spin up a sandbox (for tool execution, sub-agent creation, or session isolation) and uses the OpenShell SDK to create and manage sandboxes programmatically. The harness separates "thinking" from "execution," putting the execution into secure sandboxes while orchestration remains outside.

NOTE: OpenShell is Dev Preview in RHOAI 3.5, Tech Preview in 3.6, with GA targeted early next year. Kata Containers provide optional hardware-level isolation beneath OpenShell's application-level sandboxing for an additional defense layer.

=== Key Takeaways

* AI safety requires defense-in-depth: no single tool covers all attack vectors. The Guardrails Orchestrator + NeMo Guardrails handle runtime protection, Garak + Chatterbox validate pre-deployment, and Agent Sandbox + OpenShell provide secure runtime isolation. Kata Containers add an optional hardware-level isolation layer beneath
* Guardrails operate at both input (blocking prompt injection before it reaches the agent) and output (filtering non-compliant responses before they reach the user). The Guardrails Orchestrator is GA and coordinates detection
* Garak provides quantified adversarial robustness with pass/fail evidence. The Chatterbox integration enables a full flow: define a policy, generate synthetic attacks, probe the model, produce a compliance report
* Red Hat's approach is bring-your-own-agent with two patterns: whole-agent sandboxing (zero code changes, works for any agent) and harness-native integration (framework-level SDK). Customers keep their agent framework
* The Policy Advisor provides an iterative, audit2allow-style workflow for building least-privilege policies - start restrictive, let the agent discover what it needs, review and approve
