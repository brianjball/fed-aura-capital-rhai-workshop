=== Network and security context

NOTE: Your namespace includes NetworkPolicies that restrict east-west traffic between pods. The mortgage-ai-api pod can reach mortgage-ai-db and minio, but not pods in other namespaces. In Module 9 (AI Safety), you will explore OpenShell sandboxing, which adds application-level security on top of these network boundaries.

NetworkPolicies define which pods can communicate with each other at the network level. This is the first layer of the defense-in-depth security model you will explore in Module 9.

=== Build a conversation for later analysis

Before we move on, let's generate a richer session with multiple conversation exchanges (called "turns" in AI terminology - each turn is one question from you and one response from the agent). This will give us more data to explore when we get to tracing in Module 8.

[start=11]
. In the same chat, ask a follow-up question:
+
[source,console,role=execute,subs=attributes+]

----

. Then ask one more:
+
[source,console,role=execute,subs=attributes+]
----

----

Each question triggers a different tool call behind the scenes. By the time you finish, your CEO session will have 3 turns spanning pipeline health, denial analysis, and officer performance. In Module 8, you will trace every step of this conversation end-to-end.

=== What just happened?

The responses look great. But stop and think about what happened behind the scenes:

* Which **agent** processed your question? Was it a single agent, or did multiple agents collaborate?
* Which **tools** did the agent invoke to gather pipeline data, denial rates, and performance metrics?
* How **long** did each step take? Was the LLM call fast, or did a tool call add latency?
* What if the response was **wrong**? How would you trace back to the root cause?
* What if a tool call **failed silently**? Would you even know?

The platform captured all of it automatically. You will trace every step in Module 8 (Evaluations & Tracing).

== Exercise 3: Understand the architecture in context

Now that you have seen the platform running, let's connect what you observed to the architecture.

. Review the architecture diagram below and identify the components we've interacted with:
+
[#fed-aura-platform-architecture]
.{company_name} AI platform architecture
image::fed-aura-platform-architecture.svg[Diagram showing {assistant_name} connected to persona agents, self-hosted models, MCP tools, a RAG vector database, MLflow observability, and platform security layers,align=center]
+
The platform is built around a set of cooperating components. At the center is {assistant_name} - a set of persona-specific agents orchestrated with LangGraph and powered by self-hosted models served through vLLM. Each agent has access to domain knowledge via RAG, can call real tools via MCP, and is observable through MLflow tracing. All inference goes through the MaaS gateway, which enforces access control and usage metering. NeMo Guardrails filter inputs and outputs at the boundary. OpenShell sandboxes agent execution with deny-by-default policies.

**Mapping components to architecture:**

[cols="1,2,2",options="header"]
|===
|Pod |Architecture Role |What it does

|mortgage-ai-api
|Agent Layer (center)
|Single FastAPI pod with 5 LangGraph agent implementations. Routes requests to the right agent based on persona. Makes tool calls via MCP, queries the database, calls the LLM.

|mortgage-ai-ui
|Frontend
|React application. Renders the persona-specific interfaces (Borrower portal, CEO dashboard, etc.)

|mortgage-ai-db
|Data Layer
|PostgreSQL with pgvector. Stores application data, conversation history, and vector embeddings for RAG.

|minio
|Storage Layer
|S3-compatible object storage. Holds uploaded documents (borrower PDFs, policy files) for document processing.

|keycloak
|Identity Layer
|OIDC identity provider. Authenticates users and maps them to personas with role-based access control.
|===
